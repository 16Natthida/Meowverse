# หลักฐานการทดสอบโฟลว์รับเข้าสินค้าและรอบตกหล่น

วันที่ทดสอบ: 16 กันยายน 2569 เวลา 00:47 น. (Asia/Bangkok)

## ขอบเขต

- ใช้ฐานข้อมูลจริงจากค่าที่กำหนดใน `.env`
- ใช้ API เซิร์ฟเวอร์ที่รันจากโค้ดปัจจุบันบน `127.0.0.1:3010`
- ใช้รอบจริง `Test6` และสินค้า/บัญชีที่มีอยู่จริงในฐานข้อมูล
- สร้างออเดอร์ทดสอบชั่วคราว แล้วล้างข้อมูลทดสอบหลังจบทุกครั้ง

## เคสทดสอบ

1. สั่งสินค้า 3 ชิ้นในรอบ `Test6`
2. ตรวจรับครั้งแรก 1 ชิ้น
3. ตรวจรับของตกหล่นภายหลังอีก 2 ชิ้น
4. ตรวจสอบการแบ่งออเดอร์และการแสดงรอบในแต่ละหน้า

## ผลที่ตรวจสอบได้

| รายการ | ผลที่ได้ |
|---|---|
| ออเดอร์หลักหลังรับครั้งแรก | เหลือ 1 ชิ้น, รับแล้ว 1 ชิ้น, `Arrived` |
| ออเดอร์ลูกตกหล่น | 2 ชิ้น, รับแล้ว 0 ชิ้น, `Delayed` |
| รอบของออเดอร์ลูก | ยังคงผูกกับรอบจริง `Test6` (round id 31) |
| ระหว่างรอของ | dropdown หน้ากรอกค่านำเข้าเห็น `Test6 (ตกหล่น)` และรายการ 2 ชิ้น แม้รับแล้ว 0 ชิ้น |
| รับของตกหล่นภายหลัง | สำเร็จ: 2/2 ชิ้น, `Arrived` |
| หลังรับของตกหล่น | dropdown ยังคงมี `Test6 (ตกหล่น)` โดยใช้ round id 31 และ `fee_segment = Missing` |
| สินค้าใน segment ตกหล่น | 2 ชิ้น, รับแล้ว 2 ชิ้น |
| หน้ารอบพรีออเดอร์ทั่วไป | ไม่แสดงรอบที่ลงท้าย `(ตกหล่น)` |
| หน้ารับเข้าสินค้า | ไม่แสดงรอบที่ลงท้าย `(ตกหล่น)` |

## ตัวระบุข้อมูลทดสอบ

- ออเดอร์หลักชั่วคราว: `137`
- ออเดอร์ลูกชั่วคราว: `138`
- รอบจริงที่ใช้: `Test6` / round id `31`

## การล้างข้อมูล

หลังทดสอบตรวจสอบซ้ำแล้วพบว่าออเดอร์ชั่วคราวที่เหลืออยู่: `0` รายการ

ไม่มีการลบหรือแก้ไขออเดอร์จริงเดิมในระบบ ตัวเลข auto-increment ที่ขยับจากการสร้างข้อมูลชั่วคราวไม่กระทบข้อมูลการใช้งาน

หลังล้างข้อมูล เมื่ออ่าน API จริงของระบบที่ `127.0.0.1:3001` พบว่า `Test6` มีเฉพาะ segment หลัก เพราะขณะนี้ไม่มีออเดอร์ตกหล่นค้างอยู่ในรอบนี้ จึงยังไม่มีเหตุผลให้ dropdown แสดง `Test6 (ตกหล่น)` ค้างไว้ตลอดเวลา

เมื่อมีการตรวจรับไม่ครบ ระบบจะสร้างออเดอร์ลูกตกหล่นและทำให้ `Test6 (ตกหล่น)` ปรากฏใน dropdown อัตโนมัติ ตามผลทดสอบด้านบน
